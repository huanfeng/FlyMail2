# AI 多配置自动切换 + 设置页重组：方案与计划

> 状态：方案待确认（2026-09-23）。确认后按「阶段」逐个实施，每阶段独立可提交、测试全绿。

## 0. 现状

**AI 翻译（M16，尚未提交）**

- 配置是 `settings` 表里的三个键：`ai_base_url` / `ai_api_key`（密文）/ `ai_model`，外加 `translate_target_lang`。
- `translate.Service` 每次翻译现取一份 `Settings`，`ai.New` 建一个客户端，`runChunks` 3 并发分批调用。
- 错误分两类：不可重试（401/403/404/400）→ fatal 整体失败；可重试（429/5xx/网络）→ 该批退回原文。
- 问题：只有一个出口。余额用完、被限流、服务商宕机时，翻译直接不可用，只能手动去设置页改。

**设置页**

- `SettingsDialog.tsx` 1439 行，左侧 17 个平铺入口，无分组。
- 其中 9 个分区（资料/外观/通用/账户/同步/隐私/安全/快捷键/关于）是写在同一文件里的内联组件。
- 归类不一致：
  - 「通用」只有一个语言选项；「安全」只有改密码。
  - 「邮件」页把**同步参数**（系统级）和**会话视图**（阅读偏好）、**重建索引/线程**（维护操作）混在一起。
  - 「对外访问地址」放在通知页，但它还是 OAuth 回调、深链的共同依赖。
  - 「隐私」和「黑名单」都挂着 shield/cloud 图标，和「OAuth」图标重复。

## 1. AI 多配置与自动切换

### 1.1 数据模型：新表 `ai_providers`

不再用 KV 存 JSON 数组。改建一张表，理由：每条配置的密钥要单独加密、单独「清除」；排序可以复用账户那套 `sort_order` + `lib/reorder.ts`；以后要统计用量，也有地方挂字段。

```go
type Provider struct {
    ID        uint
    Name      string // 用户起的名字，如 "DeepSeek 主力"、"本机 Ollama"
    BaseURL   string // 落库前经 ai.Endpoint 归一
    APIKey    string // 密文，永不出网，对外只给 key_set
    Model     string
    Enabled   bool   // 关掉 = 留着配置但不参与切换
    SortOrder int    // 越小越先用
    CreatedAt, UpdatedAt time.Time
}
```

**「使用列表」**就是：`enabled = true` 的配置按 `sort_order` 排出来的顺序。界面上可以拖动（或上移/下移）改顺序，用开关决定参不参与切换。目前只有翻译一个用途，所以只做一条列表；以后加摘要之类的用途，再给每个用途配一条自己的列表（YAGNI，这次不做）。

**迁移**：启动时如果 `ai_providers` 为空、旧键 `ai_base_url` 又有值，就插入一条「默认」配置（密文原样搬过去，不需要解密），再删除三个旧键。迁移做成幂等的，加单测覆盖。

### 1.2 运行时状态（内存，不落库）

每条配置维护一份健康状态：

| 字段 | 用途 |
|---|---|
| `CooldownUntil` | 冷却截止时间。冷却中的配置排到队尾 |
| `LastError` / `LastErrorKind` | 界面显示「余额不足 · 14:20」 |
| `LastOKAt` | 界面显示「正常 · 上次成功 3 分钟前」 |
| `Failures` | 连续失败次数，用来做指数退避 |

不落库的理由：冷却是几十秒到几十分钟级别的事，重启后重新探一次，代价只是一次失败请求。落库还得处理状态过期。

### 1.3 错误分类 → 切换策略

`ai.APIError` 需要补两个字段：上游 `error.code` / `error.type`，以及 `Retry-After`。有了它们，才能区分「限流」和「余额用完」——两者可能都是 429。

| 分类 | 判据 | 切换 | 冷却 |
|---|---|---|---|
| 余额/配额耗尽 | 402；429/403 且 code/type/消息里含 `insufficient_quota`、`billing`、`balance`、`余额`、`欠费` 等 | ✅ | 长：1 小时 |
| 鉴权失败 | 401 / 403（非 billing） | ✅ | 长：30 分钟（配置问题，不要反复撞） |
| 限流 | 其余 429 | ✅ | `Retry-After`，没有就 60s，按次数指数退避，上限 10 分钟 |
| 上游故障 | 5xx、连接失败、超时 | ✅ | 短：30s 起，指数退避 |
| 模型/请求不被接受 | 404、400 | ✅ | 中：10 分钟（这家不认这个模型，换一家可能认） |
| 输出被截断 | `ErrTruncated` | ✅ | 不冷却（与内容长度有关，不是这家坏了） |
| 用户离开 | `context.Canceled` | ❌ | — |

规则只有一条：**只要不是用户取消，就换下一家**。区别只在冷却多久。

### 1.4 切换机制：整封重翻（已确认）

**一封信的译文只出自一个配置**，保证风格和术语一致。代价是切换时，已经翻好的批次会作废，重复计费；可以接受。

`translateDetail` 外面套一层循环，按使用列表依次尝试：

```
for p in 候选顺序(使用列表, 健康状态):
    重置所有 segment 的译文
    err := runChunks(ctx, client(p), ...)
    成功 → 记 p 健康，返回（Model = "配置名 / 模型"）
    失败 → 按 §1.3 给 p 记冷却，换下一个，整封重来
全部失败 → ErrAllFailed，聚合每家的原因
```

- **「这一家失败」的判据比现在严格**：只要有**任何一批**出错（包括 429/5xx 这类可重试错误），就立即取消这一家的其余批，整封换下一家。
  - 现行的「个别批退回原文、其余照常」只保留给**最后一个候选**：已经没有下家可换时，部分译文仍然比什么都没有强。
- **冷却中的配置排到队尾，不跳过**：全员都在冷却时，仍按「最早解冻」的顺序去试，而不是直接拒绝。用户点了翻译，就要真的去试。
- **全部失败时的报错**：返回 `ErrAllFailed`，把每家的原因拼在一起，例如「3 个 AI 配置均失败：DeepSeek 余额不足；OpenAI 限流（429）；本机 Ollama 连接被拒绝」。
- **健康状态的记录**：放在全局的 `ai.Health`（按 provider ID 索引），由 `translate.Service` 读写。
- **`ctx` 取消**（用户关掉了邮件）：立即停止，不切换，也不给当前配置记冷却。
- **`Translation.Model` 的记法**：改为「配置名 / 模型」。

### 1.5 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/ai/providers` | 列表 + `key_set` + 运行时状态 |
| POST | `/ai/providers` | 新建（base_url 归一校验与现在相同） |
| PUT | `/ai/providers/:id` | 修改；`api_key` 留空表示不改，传 `clear_key` 表示清除 |
| DELETE | `/ai/providers/:id` | 删除 |
| PUT | `/ai/providers/order` | 按 id 数组重排 |
| POST | `/ai/providers/:id/test` | 发一次极短对话，返回耗时或分类后的错误，并清除/写入冷却状态 |
| POST | `/ai/providers/:id/reset` | 手动解除冷却（「我已经充值了」） |

`translate_target_lang` 仍留在 settings KV 里（它是翻译偏好，不属于某个配置）。`/translate/languages` 的 `enabled` 改为「至少一条启用的配置」。

### 1.6 前端：AI 页

```
AI 翻译
├─ 翻译偏好：默认目标语言
└─ 接口配置（按顺序依次尝试，失败自动切到下一个）
   ┌──────────────────────────────────────────────────────┐
   │ ⠿ ① DeepSeek 主力   deepseek-chat · api.deepseek.com   │
   │      ● 正常 · 3 分钟前成功        [测试] [编辑] [开关]    │
   │ ⠿ ② OpenAI 备用     gpt-4o-mini · api.openai.com       │
   │      ◐ 冷却中至 15:20 · 余额不足   [解除] [编辑] [开关]    │
   │ ⠿ ③ 本机 Ollama     qwen2.5:7b · 127.0.0.1:11434       │
   │      ○ 已停用                                          │
   └──────────────────────────────────────────────────────┘
   [+ 添加配置]
```

- 编辑用对话框（沿用现有字段、预设按钮和密钥占位语义），复用 `ChannelDialog` 的写法与防误触规则。
- 排序复用 `lib/reorder.ts`（与账户排序一致）。
- 阅读器里提示「未配置 AI」时，加一个直达按钮，打开设置并定位到 AI 页（依赖 §2 的 `openSettings(sectionId)`）。

## 2. 设置页重组

### 2.1 新信息架构（17 个平铺 → 5 组 14 页）

| 组 | 页面 | 内容（来源） |
|---|---|---|
| **个人** | 个人资料与安全 | 资料 + 修改密码（原「资料」「安全」合并） |
| | 外观与语言 | 主题、布局、模式 + 界面语言（原「外观」「通用」合并） |
| | 快捷键 | 不变 |
| **邮箱** | 账户 | 账户列表、排序、导入导出 |
| | 阅读 | 会话视图（从「邮件」页移来）+ 远程图片、信任名单（原「隐私」） |
| | 撰写 | 签名 + 别名（两个区块） |
| | 过滤 | 规则 + 黑名单（两个区块） |
| | 同步 | 同步深度、轮询间隔、正文预取（原「邮件」页的同步部分） |
| **通知** | 通知 | 浏览器提醒、推送渠道、推送正文 |
| **集成** | AI 翻译 | §1.6 |
| | OAuth 应用 | 不变 |
| **系统** | 服务器 | 对外访问地址（从通知页移来）+ 维护：重建索引、重建会话线程（从「邮件」页移来） |
| | 监控 | 不变 |
| | 关于 | 不变 |

依据：

- 按「谁在什么时候来改」分组。个人偏好常改；邮箱行为偶尔改；集成和系统配一次就不再动。
- 一页只回答一类问题。「邮件」页拆开后，同步、阅读、维护各归其位。
- 顺手修正重复图标（shield 出现了两次）。

### 2.2 代码结构

- 把 `SettingsDialog.tsx` 里 9 个内联分区拆成独立文件，放在 `components/settings/sections/`。
- 新增 `settings/registry.ts`，每页一条 `{ id, group, labelKey, icon, Component }`。导航和内容都由它生成。
  - 加一页只需加一行注册，不必在两处各补一段 `section === 'x'`。
- 预期 `SettingsDialog.tsx` 缩到 ~250 行，只剩外壳、分组导航和移动端适配。
- `SettingsDialog` 增加 `initialSection` 属性，`Shell` 暴露 `openSettings(id)`，供 §1.6 的直达按钮使用。
- 旧 section id 做一次映射（`security→profile`、`general→appearance`、`blocklist→filters`、`privacy→reading`、`mail→sync`、`signature/aliases→compose`），避免外部引用失效。
- 移动端：分组标题在窄屏下拉/抽屉里同样显示（沿用现有 sd-nav 的移动适配）。

### 2.3 可选（本次不默认做）

- 设置内搜索框：registry 里加 `keywords` 即可支持。页数少了以后价值不大，先不做。
- 通知页区块多，再加页内子标签。先看合并后的实际长度再决定。

## 3. 实施计划

**阶段 0：收拢现有未提交工作**
工作区里还有 M16 AI 翻译、OAuth 提供方区分、账户停用与排序、通知正文等多批改动没有提交。先按功能分批提交（`git commit --only`，不用 `add -A`），让后面的重构有干净的基线，也能单独回退。

**阶段 1：后端，多配置存储与迁移**
- 内容：`ai_providers` 模型、仓储、CRUD 与排序接口，从旧键迁移。
- 测试：迁移幂等（空表、有旧键、已迁移三种情况）；密钥不回显；base_url 归一；排序。

**阶段 2：后端，整封切换与健康状态**
- 内容：给 `APIError` 补 code 和 Retry-After；错误分类；`ai.Health`；`translate` 外层循环；test/reset 接口。
- 测试：
  - 分类表逐行覆盖（每一类用 httptest 伪造上游）；
  - A 余额不足 → B 整封重翻成功，A 进入冷却，译文只含 B 的结果；
  - A 某一批 429 → 取消 A 的其余批，整封换 B；
  - 最后一个候选的部分失败仍返回部分译文；
  - 全员失败时聚合错误；
  - 全员冷却时仍会去试；
  - 用户取消不切换、不记冷却（开 `-race`）。

**阶段 3：前端，AI 页改为多配置列表**
- 内容：列表、编辑对话框、测试/解除/开关/排序；移除旧单配置表单；中英文案。
- 测试：vitest 覆盖增删改、排序、状态徽标、密钥占位语义。

**阶段 4：前端，设置页重组**
- 内容：拆分内联分区、registry、分组导航、合并页面、`initialSection` 与旧 id 映射；阅读器「去配置」直达。
- 测试：现有 SettingsDialog 测试迁移过来；每页都能打开；旧 id 能跳到新页；移动端导航快照。

**阶段 5：端到端验收**
- 本机起服务，用两个假上游（一个固定回 429 insufficient_quota，一个正常）跑一次真实翻译，确认切换、冷却、界面状态都正确。
- 桌面宽屏和窄屏各走一遍设置页的全部分页。
- 更新 `docs/flymail/m16-ai-translate.md`。
