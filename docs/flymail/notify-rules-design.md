# 通知规则层：设计约束与待决问题

> 状态：**未实现**，仅记录约束。2026-09-17 记。
>
> 缘起：做完「推送内容按渠道分三档 + 飞书卡片」之后，用户提出还要预留规则与模板。
> 模板已经留好了位置（`Channel.Template` 字段 + 渲染集中在 `notify/render.go`），
> 规则这一层因为和现有规则引擎的边界没划清，先不动手，把约束记下来。

## 一句话

通知规则要回答的是「**这条通知该不该发、发给谁**」，而不是「这封邮件该怎么处理」。
后者已经有 M11 的邮件规则引擎了。

## ⚠ 最大的风险：两套条件系统打架

系统里**已经有一套规则引擎**（`modules/email/rule`，M11），它有完整的条件匹配
（发件人、主题、正文、附件名……）和动作，其中一个动作就是「触发通知」。
所以今天已经能做条件推送：配一条「发件人是老板 → 触发通知」的规则即可。

如果通知层再长出一套自己的条件匹配，用户会面对两个都能配「来自老板的邮件」的地方，
而它们的语义微妙不同：

| | 邮件规则（M11） | 通知规则（设想） |
|---|---|---|
| 作用对象 | 邮件 | 通知 |
| 触发时机 | 同步时，每封新邮件一次 | 通知发出时 |
| 典型动作 | 移动、标记、加标签、触发通知 | 选渠道、改档位、静音、合并 |
| 幂等 | 有 `rule_runs` 保证 | 无状态 |

**边界建议**：通知规则只做「邮件规则表达不了」的那部分——

- **时间维度**：工作时间外不推送、夜间静音、周末只推高优
- **渠道路由**：同一条通知按条件发往不同渠道（工作邮件→飞书，账单→私人 webhook）
- **档位覆盖**：某类邮件强制降到「基本信息」（例如来自银行的邮件不带正文）
- **频率控制**：同一发件人 N 分钟内合并成一条；单位时间上限

而「哪些邮件值得提醒」应当继续留给邮件规则——它已经有匹配能力、有幂等保证，
而且用户已经在那里配过了。

## 技术约束（做的时候必须满足）

1. **不能在投递 worker 里做重活**。`notify.Service` 的 worker 是单条 goroutine 串行
   消费 `s.ch`，队列满了会**直接丢弃外发**（`service.go` 的 `select/default`）。
   规则匹配如果要查库，得想清楚是在 `Emit` 之前还是之后。

2. **静音/合并需要状态**，而目前 notify 是无状态的。合并「同一发件人 5 分钟内的邮件」
   要么落一张表，要么在内存里攒——后者重启即失效，且多实例下不成立。

3. **时间维度要考虑时区**。服务端时区不等于用户所在时区，`app_base_url` 那种
   「服务端猜不出来」的教训在这里同样成立：需要用户显式配一个时区，或者存 UTC 偏移。

4. **档位覆盖要和渠道配置合并**。现在档位在 `Channel.ContentLevel`，规则如果能覆盖它，
   得定义优先级（规则 > 渠道？只能降不能升？）。**建议只允许降级**——
   规则把「全文」降成「基本信息」是安全方向，反过来会让用户在渠道上配的隐私约束失效。

5. **要能看出「为什么没收到通知」**。规则一旦能拦截通知，「没收到」就有了多种原因
   （没匹配事件、被规则静音、渠道禁用、投递失败）。`notify_logs` 目前只记投递结果，
   被规则拦下的应当也留痕，否则排查无从下手。

## 待用户确认

- 规则的作用范围是全局还是按账户？
- 静音时段内的通知是**丢弃**还是**攒着稍后发**？后者要存储与补发逻辑。
- 是否需要「测试这条规则」的能力（类似邮件规则的试运行）？
