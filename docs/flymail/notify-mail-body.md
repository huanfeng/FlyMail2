# 外发通知里的邮件正文与链接

**状态**：已实现（飞书卡片 + webhook）

把邮件正文推到飞书里，有三件事各自会独立出错：正文怎么从 HTML 降成能读的文本、
链接怎么变成可点的而又不被用来钓鱼、以及多长才不会让整条消息发不出去。
这三件事分别落在 `internal/mailtext`、`feishu_card.go` 和 `fitFeishuCard` 里。

## 一、HTML 降级：为什么不复用 `fts.StripHTML`

`fts.StripHTML` 是给全文检索用的，目标是「把词切出来」：它把 `[\s\xA0]+`
**一律压成一个空格**，换行、段落、表格行全部消失。索引不在乎这个，人在乎——
八千字挤成一坨没有任何段落的墙，比不推正文还难看。

它也不该被改：`fts.StripHTML` 被注册成 SQLite 函数（`StripHTMLFuncName`）
供 FTS 触发器调用，改了它的输出，**已建好的索引与新写入的行就对不上了**。

所以另起了 `internal/mailtext`，与 FTS 那套的关键分野：

| | `fts.StripHTML` | `mailtext.Extract` |
| --- | --- | --- |
| 空白 | 所有空白压成一个空格 | 只压水平空白，`\n` 保留 |
| 块级标签 | 换成空格 | 换成换行 |
| `<td>` / `<th>` | 换成空格 | 换成空格（同一行的格子） |
| 行内标签（`b`/`span`） | 换成空格 | 直接删 |
| `<script>` / `<style>` | 整块丢 | 整块丢（含 `<head>`） |
| 链接地址 | 丢弃 | 单独提取 |

三个容易写错的细节：

- **行内标签必须删而不是换成空格**，否则 `<b>发</b><b>票</b>` 会变成「发 票」。
- **`<td>` 必须换成空格而不是删**，否则 `<td>发票</td><td>报销</td>` 粘成「发票报销」。
- **HTML 造出来的换行要全部收敛成一个**。相邻的 `</p><p>` 造出两个，嵌套 div
  每层再贡献一个。这些空行不承载作者意图。纯文本邮件走另一条路径——那里的空行
  是作者敲的，留一个。

`message.Service` 因此有两个取正文的方法，**刻意不合并**：

- `BodyText`：给规则匹配与索引用，走 `fts.StripHTML`。它的输出形态是**用户已配
  规则的匹配依据**，改它会悄悄改变现有规则的命中结果。
- `BodyForDisplay`：给推送用，走 `mailtext`，另带链接。

## 二、链接：为什么单独列出来而不是原位可点

原位可点要把正文整段交给 `lark_md` 渲染，那就正面撞上 `feishu_card.go`
开头那条安全边界：**邮件内容由发信人完全控制，而飞书不支持反斜杠转义**。

一封正文写着 `请登录 [icbc.com.cn](http://evil.com) 处理` 的钓鱼邮件，
在卡片里会渲染成一条看起来完全正经的银行链接——而且它紧挨着我们自己的
「打开邮件」按钮，可信度比在邮件客户端里更高。

所以改成单独列一区，**显示文本就是地址本身**：

```
正文中的链接
https://github.com/x/y/runs/12     ← 可点
https://github.com/settings        ← 可点
```

显示与目标既然是同一个串，就不存在「看着是 A、点过去是 B」的空间。
代价是链接脱离了上下文，但推送本来就是个索引，真要读还得点「打开邮件」。

配套的几道闸门（都在 `internal/mailtext` 与 `markdownLink`）：

- **只放行 http/https**。`javascript:`、`data:`、`file:` 混进来毫不费力——
  发信人写什么 `href` 我们就读到什么。
- **`(` `)` `[` `]` 百分号编码**。它们会提前终结 markdown 的链接构造，让后面
  本属于地址的部分溢出成普通文本；精心构造的地址能借此让显示的那段与实际跳转
  的那段分家，正是这个设计要杜绝的事。百分号编码是 URL 语义上等价的替换。
  ⚠ 显示与目标用的是**同一个**处理后的串——只转义其中一侧，恰恰会制造出不一致。
- **含 `\n` `\r` `\t` 的地址整条丢弃**，它们能在卡片里制造额外的行。
- **单条超过 300 字符丢弃**（追踪链接、base64 塞进 query 的那种），**最多 8 条**
  （营销邮件每张图每个图标都是一个链接）。
- **链接跟正文走同一道内容级别闸门**。配「基本信息」的渠道一个字正文都不带，
  链接同样不能漏——不然一封密码重置邮件的重置链接就进了多人群，比正文泄漏更严重。

## 三、长度：按字节量，不按字符算

飞书对卡片消息请求体的硬限制是 **30KB**，超了**整条发不出去**。而且是静默失败
的那种：用户看到的是「有几封邮件没推送」，不是「正文被截短了」。

字符数和字节数之间没有可用的换算：

- 中文一个字 UTF-8 占 3 字节，emoji 占 4
- JSON 转义把控制字符变成 6 字节的 `\uXXXX`

按字符算就只能取一个悲观值，结果是英文邮件白白被截掉一大半，而某些极端内容
照样能超。所以 `fitFeishuCard` 量的是**最终要发出去的那串字节**：渲染 → 序列化 →
超了就把字符上限乘 0.7 重来，直到落进 26KB（给签名、标题栏、按钮留 4KB 余量）。

逐次收缩而不是一步算出该留多少，是因为收缩正文会连带改变整个 JSON 的转义情况——
算出来的仍是估计值，量出来的才是事实。

缩到 200 字还超预算就停手：那说明撑爆预算的不是正文（超长主题、大量链接之类），
再缩只是空转，交出去让上层报错。

**用户可配的 `notify_body_runes` 是排版偏好，不是安全上限。** 无论填多大，
上面那道字节裁剪都还在。上界 20000 也不是技术限制，是「再多也没意义」。
填 0 表示用内置默认（8000）。

⚠ 前端解析这一项时**不能套 `Number(raw) || 8000`**：其它数字设置都是那么写的，
照抄过来会把 0 吞掉，而 0 在这一项里是合法取值。后果是用户存了 0、界面显示
8000，看着像没保存成功，再点一次保存就把 8000 真写进了库。
