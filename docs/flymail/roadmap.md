## 编号约定

M8 归属已完成的后端加强三部曲（结构化日志 / E2E 测试 / 同步队列 Actor 重构）。
本路线图自 **M9** 起。

## M9 — 检索重构

**问题**：`modules/email/message/repository.go` 的 `SearchMessages` 用五个字段 `LIKE '%q%'` + 全正文 JOIN，前缀通配符使索引全部失效；无搜索语法；只能搜到本地已同步内容。

**目标**：邮件量 5 万级时搜索响应稳定在 100ms 内，支持限定符语法，未同步范围有服务端兜底。

### 范围

1. **FTS5 虚表**
   - 新建 `messages_fts`（`subject`、`from_name`、`from_addr`、`snippet`、`text_body`），`content=` 外部内容模式挂到 `messages` 避免正文双份存储
   - 用 SQLite 触发器（INSERT / UPDATE / DELETE）维护索引，正文入库路径 `StoreParsedBody` 落库后自动生效
   - 首次启动时对存量数据做一次性回填，带进度日志；GORM `AutoMigrate` 管不了虚表，需要在 `internal/database/database.go` 里走裸 SQL 分支
   - 中文分词：SQLite 默认分词器对中文按整串处理。评估 `unicode61` + trigram 分词器（SQLite 3.34+ 支持 `tokenize='trigram'`），或落在应用层做二元切分后入索引

2. **搜索语法解析器**
   - 支持 `from:`、`to:`、`subject:`、`has:attachment`、`is:unread`、`is:starred`、`before:`、`after:`、`in:<folder>`、`account:`
   - 限定符走结构化 WHERE 条件，自由词走 FTS5 MATCH，两者 AND 组合
   - 解析器独立成文件并配单元测试（含引号包裹、多限定符、非法输入回退为纯文本搜索）

3. **IMAP SEARCH 兜底**
   - 本地结果不足且用户显式请求时，向 runner 投递前台任务执行 IMAP `SEARCH`，命中的 UID 补同步后并入结果
   - 必须走现有前台队列，不得新建连接

4. **前端**
   - 搜索栏支持语法输入 + 限定符提示
   - 结果高亮命中词
   - 保留分页（现有 `beforeDate` / `beforeID` 游标语义不变）

### 验收标准

- [ ] 5 万封邮件的库中，任意关键词搜索 P95 < 100ms（对比改造前记录数据）
- [ ] `from:zhang subject:发票 has:attachment` 能正确返回交集结果
- [ ] 中文关键词可命中主题与正文
- [ ] 解析器单元测试覆盖全部限定符 + 3 类非法输入
- [ ] 存量库升级后无需手动操作，回填过程有日志可见
- [ ] IMAP SEARCH 兜底不阻塞前台操作（诊断面板队列深度无异常堆积）

### 风险

- FTS5 外部内容模式的触发器写错会导致索引与主表漂移 → 提供一个"重建索引"的运维入口
- 中文分词方案选错会让搜索"看起来能用但漏结果" → 分词方案定下来前先写一组中文检索用例

## M10 — 会话线程

**问题**：`Message` 模型已有 `MessageID` / `InReplyTo` / `References` / `ThreadID` 且带索引，但后端无聚合查询、前端无折叠，能力完全闲置。

**目标**：列表按会话折叠，Reader 内手风琴展开整条往返。

### 范围

1. **后端**
   - 核实现有 `ThreadID` 的生成逻辑是否可靠（`References` 链 + 主题归一化兜底），补齐缺失场景
   - 新增会话聚合查询：按 `thread_id` 分组，返回会话代表信息（最新一封的主题/时间、参与者去重列表、封数、未读数、是否含附件/星标）
   - 分页游标需适配分组语义（按会话最新时间排序，不能沿用单封的 UID 游标）
   - 单封视图与会话视图并存，由用户偏好切换，默认会话视图

2. **前端**
   - `MailList.tsx` 会话行：参与者列表 + 封数徽标 + 未读加粗
   - `Reader.tsx` 手风琴：默认展开最新一封与所有未读，其余折叠
   - 引用内容折叠（`>` 引用块与 `<blockquote>` 收起为「显示引用内容」）
   - 会话级操作：整条标记已读 / 加星 / 移动 / 删除

### 验收标准

- [ ] 一条 10 封往返的讨论在列表中占 1 行，展开后按时间正序显示 10 封
- [ ] 跨文件夹会话（收件箱的来信 + 已发送的回复）能合并到同一条
- [ ] 会话级操作对整条内所有邮件生效，且经现有回写队列同步回 IMAP
- [ ] 切换回单封视图不丢失任何现有能力
- [ ] 聚合查询在 5 万封库中 P95 < 100ms

### 依赖

无硬依赖。与 M9 同属 message 模块，若两者相继执行可复用同一批查询性能基准。

## M11 — 规则引擎 + 黑名单

**问题**：聚合收件箱已经能把多账户混流，但没有任何过滤手段，账户越多噪音越大。

**目标**：邮件入库后自动执行用户定义的规则，黑名单前置短路。

### 范围

1. **数据模型**
   - `inbox_rules`：名称、启用开关、优先级序号、匹配模式（全部满足 / 任一满足）、条件列表、动作列表、命中后是否停止后续规则
   - 条件字段：发件人、收件人、抄送、主题、正文、任意邮件头、是否有附件、附件名、账户
   - 条件运算：包含 / 不包含 / 等于 / 正则 / 开头是 / 结尾是
   - 动作：移动到文件夹、标记已读、加星、删除、打标签、触发 IM 通知、停止处理
   - `block_list`：发件地址或域名，命中直接移入垃圾箱

2. **执行位置（关键设计点）**
   - 落在**同步入库之后、通知派发之前**：黑名单短路 → 规则引擎 → 通知派发
   - 产生 IMAP 副作用的动作（移动、删除、标记）必须走现有回写队列 `wbstore` / `writeback`，不得绕过——否则熔断与重试语义失效
   - 规则执行需幂等：同一封邮件重复同步（UIDVALIDITY 重置等场景）不得重复执行动作

3. **前端**
   - 设置页规则编辑器：条件/动作可视化增删、拖拽排序调整优先级
   - 「在已有邮件上试运行」预览命中结果，执行前可见影响面
   - 黑名单管理页 + 从邮件右键「屏蔽此发件人」

### 验收标准

- [ ] 规则命中后动作正确执行，且 IMAP 侧状态一致（重启后不回滚）
- [ ] 黑名单命中的邮件不进入收件箱、不触发 IM 通知
- [ ] 规则按优先级顺序执行，「停止处理」生效
- [ ] 同一封邮件重复入库不重复触发动作（幂等性测试）
- [ ] 试运行只读，不产生任何副作用
- [ ] E2E 覆盖：GreenMail 投递一封命中规则的邮件 → 断言落到目标文件夹

### 风险

- 规则动作与同步引擎的交互是本里程碑最大风险点。**先写清楚回写路径的时序图再动手**，参考同步队列的设计文档。

## M12 — 阅读隐私与安全加固

**问题**：HTML 邮件无服务端净化，远程图片与 CSS `url()` 外链未剥离——每次打开邮件都在向发件人回报已读、IP 与时间。

**目标**：默认不发起任何邮件内容触发的外部请求。

### 范围

1. **服务端 HTML 净化**
   - 引入 `bluemonday`（Go 生态标准选择），在 `/messages/:id` 返回正文前净化
   - 白名单标签与属性，剥离 `<script>` / `<iframe>` / 事件处理器
   - **提取所有远程资源引用**（`<img src>`、CSS `url()`、`background`）替换为占位符，原始 URL 单独返回给前端

2. **远程图片阻断**
   - 默认阻断，Reader 顶部显示「此邮件包含 N 个远程图片 · 显示图片」
   - 用户点击后按需加载；可按发件人加入白名单（记住选择）
   - 内联附件（`cid:`）走本地附件端点，不受阻断影响

3. **iframe sandbox 加固**
   - 现状 `Reader.tsx` 使用 `sandbox="allow-same-origin allow-popups"` + `srcDoc`，`allow-same-origin` 仅为父窗口量取高度
   - 改为 `postMessage` 上报高度，去掉 `allow-same-origin`，恢复完整沙箱隔离
   - 在代码注释中明确：**任何情况下不得同时开启 `allow-same-origin` 与 `allow-scripts`**

4. **登录限流**
   - `/auth/login` 按 IP 限流（参考 MailFlow：15 分钟 10 次）
   - 失败计数落 SQLite，重启不清零
   - 触发限流后返回 429 并记结构化日志

### 验收标准

- [ ] 打开含追踪像素的邮件，浏览器 Network 面板无任何外部请求
- [ ] 点击「显示图片」后正常渲染，加入白名单后同发件人后续邮件自动加载
- [ ] 含 `<script>` 的恶意 HTML 邮件净化后无脚本残留（单元测试固定样本）
- [ ] iframe 高度自适应在去掉 `allow-same-origin` 后仍正常工作
- [ ] 连续 11 次错误登录后第 11 次返回 429

## M13 — 撰写器升级

**问题**：`react-simple-wysiwyg` 能力不足以支撑正式回复场景。

### 范围

- 替换为 **Tiptap**（ProseMirror 内核，React 生态成熟、可裁剪）
- 签名管理：按账户配置，新建/回复分别可选是否插入
- 引用折叠：回复时自动折叠原文，可展开编辑
- 内联图片：粘贴/拖入自动上传为 `cid:` 内联附件
- 富文本工具栏：字号、颜色、高亮、列表、链接、表格
- 发件人别名（alias）支持：账户下可配多个发信地址

### 验收标准

- [ ] 从 Outlook / Gmail 粘贴的富文本保留格式
- [ ] 内联图片在收件方（Gmail / Outlook）正确显示
- [ ] 签名按账户正确插入，切换发件账户时同步切换
- [ ] 别名发信时 `From` 头正确，且通过 SPF 校验的服务器能正常投递
- [ ] 现有草稿的读写兼容不破坏

## M14 — OAuth2 接入

**问题**：`core/imap/xoauth2.go` 有底层能力但 backend 无授权流程，微软停用基本认证后 Outlook.com / M365 账户接不进来。

### 范围

- 授权码流程（Google / Microsoft 工作账户）与设备码流程（Microsoft 个人账户）
- token 加密持久化（复用 `internal/crypto`）+ 过期前自动刷新
- 刷新失败时的账户状态标记与前端重新授权引导
- 复用 mail2im `oauth-proxy` 的既有经验，评估是否需要同类中转
- 账户添加向导中提供 Gmail / Outlook 预设入口

### 验收标准

- [ ] Gmail 账户经 OAuth 授权后可正常收发
- [ ] Outlook.com 个人账户经设备码流程接入成功
- [ ] token 过期前自动刷新，用户无感
- [ ] 刷新失败时账户进入明确的「需重新授权」状态，诊断面板可见
- [ ] token 在数据库中为加密存储

### 依赖

需要注册 Google Cloud 项目与 Azure 应用，属外部准备工作，**提前一个里程碑启动申请**。

## M15 — 分发就绪

**问题**：目前只有 `dev.ps1`（开发用途，仅监听 127.0.0.1），没有任何面向他人的分发路径。

### 范围

- 多阶段 `Dockerfile`（前端构建 → 后端编译 → 精简运行镜像），目标镜像 < 50MB
- `docker-compose.yml`：单服务 + 数据卷（无需 pg / redis，这是相对 MailFlow 的部署优势，应在文档中突出）
- 反向代理文档（nginx / Caddy）与 HTTPS 说明
- 数据备份与恢复文档（SQLite 单文件，`sqlite3 .backup` 热备份）
- 生产配置：监听地址、日志级别、数据目录的环境变量约定（注意 viper env 绑定的既有陷阱）
- Wails 桌面端打包发布：Windows / macOS 安装包 + GitHub Release 流程
- 面向使用者的 README（区别于当前的开发者视角）

### 验收标准

- [ ] `docker compose up -d` 在干净机器上一次成功启动
- [ ] 镜像体积 < 50MB
- [ ] 备份 → 删库 → 恢复流程验证通过
- [ ] 桌面端安装包在干净 Windows 上可安装运行
- [ ] README 中的部署步骤由未参与开发者复现成功

## M16 — 长尾体验

优先级最低，可按个人使用频率挑选实施：

- **一键退订**：解析 `List-Unsubscribe` 与 `List-Unsubscribe-Post`，支持 One-Click（RFC 8058）
- **Snooze**：稍后提醒，到点回到收件箱顶部
- **邮件分类标签页**：基于头部检测 + 发件人启发式（非 AI）分为 主要 / 订阅 / 社交 / 通知
- **Web Push**：PWA 推送，补齐 IM 通知之外的浏览器原生通道
- **快捷键自定义**：现有 `shortcuts.ts` 已有基础，扩展为可配置
- **联系人库**：从当前的发件人聚合升级为独立实体，支持手动编辑与头像
