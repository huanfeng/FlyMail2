# M16 — AI 邮件翻译

**状态**：代码完成，本机端到端验证通过（假 OpenAI 服务）
**优先级**：P2

## 问题

自部署邮箱收到的外文邮件（发票、订阅、服务商通知）只能靠复制到别处翻译，
而正文里的排版、图片和链接在复制粘贴时全丢了——要点的那个链接恰恰是最需要的东西。

## 决策

| 维度 | 选择 | 为什么 |
|---|---|---|
| 接口形态 | OpenAI 兼容单配置 | 它已是事实标准：OpenAI / DeepSeek / 智谱 / 硅基流动 / OpenRouter，以及本机的 Ollama / LM Studio / vLLM 全都提供 `/chat/completions`。为 Anthropic、Gemini 各写一套原生协议，换来的只是少填一个 base_url |
| 正文处理 | 解析 HTML 取文本节点，分块翻译后按序回填 | 整段 HTML 丢给模型会被改写结构（丢属性、改嵌套、"优化"掉 `<img src="cid:...">`），而且模型输出会当 HTML 渲染 |
| 展示 | 工具栏按钮整体切换译文 ↔ 原文 | 上下对照在长邮件里要滚很久；逐段对照要求译文能按段落对齐，只在纯文本方案下可靠 |
| 范围 | 主题 + 正文 | 主题和正文放在同一批里送，模型能借正文的上下文翻主题（"Re: Order 1234" 该怎么翻取决于正文在说什么） |
| 语言识别 | 本地做（Unicode 区间 + 停用词） | 交给 AI 就得先花一次调用才知道这次调用本来不必发生，而绝大多数邮件是用户自己那门语言写的 |
| 缓存 | 按 `(message_id, target_lang)` 落库，不过期 | 邮件会被反复打开。不缓存的话账单按阅读习惯增长，而不是按邮件数量增长。已收到的邮件内容不会再变，译文也就不会过时 |

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/translate/languages` | 目标语言清单 + 默认值 + AI 是否已配置 |
| GET | `/messages/:id/translation?lang=&remote=` | **只查缓存**，不触发任何 AI 调用；没翻过回 204 |
| POST | `/messages/:id/translate` | body `{lang?, force?}`；缓存优先，`force` 才真的重新花钱 |

查与写分成两个接口，是为了让界面在打开邮件时就能问一句"这封翻过没有"而不产生用量——
翻过的话按钮显示成「显示译文」，点下去是纯本地切换。

## 关键判断与踩过的地方

### 1. 译文的安全性来自"回填的是文本节点"

回填走 `node.Data`，`html.Render` 出去时 `<` `>` `&` 一律转义。模型即使返回
`<script>alert(1)</script>`，渲染出来也只是这几个可见字符。这条比任何过滤都可靠，
因为它不依赖"我有没有想到某种绕法"。出站仍然再过一遍 `htmlsan`——译文与原文走同一道门。

### 2. 缓存存未净化的 HTML，净化放在出站

反过来做的话，第一次请求把远程图换成的占位符会被缓存下来，用户此后再点
「显示图片」也换不回来——一次性的选择被缓存成了永久的。
（`handler_test.go: TestRemoteCanBeAllowedAfterCaching` 钉的就是这条，
连同"上一趟的净化不能污染缓存对象"。）

### 3. 编号协议选 `⟦N⟧` 而不是 JSON

JSON 数组要求模型对引号、换行、反斜杠正确转义，错一个整批解析失败——
而"整批失败"意味着这一段正文全是原文。编号标记没有任何转义规则可犯错，
某一段坏了也只坏那一段。解析刻意宽松：只找标记，标记之间的一切都算译文，
所以模型在开头加一句"好的，以下是译文："也不影响。

### 4. 文本节点的首尾空白必须自己留着

`word <b>bold</b>` 里的那个空格就在文本节点末尾。连同文本一起交给模型，
模型会顺手把它吃掉，于是译文变成"词粗体"。分段时把首尾空白剥出来，回填时原样拼回去。

### 5. 错误要分级，不能一句"请稍后重试"了事

- 401 / 400 这类**不可重试**的：第一批失败就 cancel 掉其余批，整体失败，HTTP 400。
  后面的批必然同样失败，继续发只是把同一个错误重复几十遍，还要用户多等几十秒。
- 偶发失败：那一批退回原文，其余照常显示。一封信里几段没翻，比整封失败有用。
- **一段都没翻出来时，报第一个错误的原话**。这是真机验证抓到的：
  把地址指向没人监听的端口，用户原本看到的是"AI 没有返回可用的译文，请稍后重试或更换模型"——
  照着这句换十个模型也没用，真正的原因（connection refused）一个字都没露出来。

### 6. 不发 temperature / max_tokens

新一代推理模型对这两个参数要么不接受、要么语义变了，发过去直接 400；
而它们的默认值对翻译足够好。少发一个参数就少一类"换个模型就报错"的故障。
代价是要自己检测 `finish_reason == "length"` 并当错误报出去——
翻译被截断的表现是"译文只有前半篇"，而前半篇看起来完全正常。

### 7. 语言识别判不准时返回空串

硬猜一个语言会把翻译按钮错误地灰掉（"这封已经是中文了"），
而猜错的代价是用户想翻译却翻不了。识别结果只用来**提示**，从不禁用按钮。

### 8. 会话视图只翻"当前那一封"

工具栏上那颗按钮跟回复/转发一样打在 `activeId` 上。一次翻译整条会话（可能十几封）
不是用户按下按钮时想要的事，那会在他没预期的情况下花掉十几倍的用量。

### 9. 新增了一条级联删除的守卫

`message_translations` 按 `message_id` 挂在邮件上，加进了 `account.MessageOwnedTables()`。
顺手补了一条守卫测试（扫库里所有带 `message_id` 的表是否都在清单里），
它当场抓出 `notifications` 也带 `message_id`——那是**有意**的例外（通知是"这件事发生过"的记录，
性质接近日志），已在测试里显式登记并写明理由。

## 预算闸门

| 闸门 | 值 | 作用 |
|---|---|---|
| `maxPartRunes` | 1200 | 单个片段上限，超了按句末拆开，防止撞上 max_tokens |
| `maxChunkRunes` | 3000 | 一次请求的字符预算，让零碎片段凑批走完 |
| `maxTotalRunes` | 60000 | 一封邮件单次翻译的总预算，超出部分保留原文并标记 `partial` |
| `chunkConcurrency` | 3 | 并发批数，在"别让用户干等"与"别撞限流"之间取值 |

没有 `maxTotalRunes` 的话，一封几 MB 的营销邮件按一下翻译就会发出几十上百次请求。
